## Dev-mode note (halol)
Be explicit with the user: a large share of what feels like "freezing" is Next.js dev-server on-demand compilation, not the app's code. Under `next dev` (the `dev:fast` server on port 3100), the FIRST visit to each route triggers a ~1000ms cold compile (route chunk + all its imports), and any barrel-heavy route (every page importing @moysklad/ui, which is not tree-shaken in dev) compiles more modules than it ships. That entire cost disappears in a production build (`pnpm --filter web build && next start`, or the prod server on 3010) where routes are pre-compiled and code-split. ACTION FOR THE USER: before judging performance, test on a production build — that alone removes essentially all of the cold-page-load lag and most "the app froze when I clicked into a section" reports. What a prod build does NOT fix, and what is genuinely in the code: (a) the re-render storms felt on EVERY interaction independent of build — skeleton-flash on list pagination/sort/search (RQ-1), full-table re-render on mouse hover (RR-4), full-editor re-render on each keystroke while typing document lines (PositionRow cluster); and (b) latency that scales with data — serial DB round-trips, ILIKE searches with no trigram index, missing sort/filter indexes, and the counterparty detail's 19 parallel list calls. Rough split at today's data volume: perceived "cold open" lag is ~70% dev-mode compilation; the remaining "it's sluggish while I use it" lag is ~100% real code (re-render + latency) and is what this backlog targets. Recommend the user reproduce complaints on the prod build first, then prioritize by whichever of the two experiences (cold-open vs in-page interaction) they actually hit most.

## Xulosa
The perceived "freezing/lag" has three distinct sources, and they need to be separated before chasing code: (1) Next.js dev-mode cold compilation (~1000ms per route the first time it's visited, entirely absent in a production build) — this is the single biggest contributor to the "it froze when I opened a page" feeling and is NOT a code bug; (2) client-side re-render storms that are felt on every keystroke/hover/pagination regardless of build (skeleton-flash on list navigation, whole-table re-render on hover, whole-editor re-render on each character typed) — these are real and persist in prod; (3) network/DB latency that grows with data volume (serial round-trips, missing indexes, 19-way client fan-out). The highest-leverage instant wins are almost free: one global react-query line (placeholderData: keepPreviousData) removes the skeleton flash on every list pagination/sort/filter/search across ~90 pages; a ref-instead-of-state hover fix kills a re-render storm; two lines of bundle config shrink first-load JS on every route. The editor typing-lag fix (memoize PositionTable rows) is the most viscerally felt but is medium-risk medium-effort, so it comes right after the free wins. DB index migrations are cheap, additive, and future-proof the app as data grows.
